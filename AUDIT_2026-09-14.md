## 2. Дефекти, знайдені цією ревізією

### 2.1 `_emergency_respawn`: контракт `KickResult` не доїхав, аварійна гілка мертва

**Це найважливіше з усього документа.**

`orchestrator.py`, рядки 1032–1043:

```python
res1 = self.kicker.smart_perturbation_kick(self.run_best_sol, T=1.0)
forced_rescue = res1[0] if (isinstance(res1, tuple) and len(res1) > 0) else None
...
    res2 = self.kicker.smart_perturbation_kick(self.run_best_sol, T=0.6)
    healed_seed = res2[0] if (isinstance(res2, tuple) and len(res2) > 0) else None
```

Етап 3 (§13.1 вашого плану) замінив кортежі різної арності на `KickResult` —
`@dataclass`, не кортеж. `_apply_kick` переведено, а ці два виклики — ні.
`isinstance(res1, tuple)` тепер **завжди False**, отже `forced_rescue` і `healed_seed`
**завжди None**.

Перевірено на `FakeSimulator`:

```
тип результату кіка: KickResult
кік успішний (res1.failed == False): True
рішення, яке кік повернув: [2, 0, 2, 2, 2, 2]
forced_rescue за поточним кодом orchestrator.py: None
```

Наслідки, по порядку:

1. Дві симуляції (мінімум — `smart_perturbation_kick` ще й лікує мережу, тобто
   витрачає більше) виконуються, і результат викидається.
2. Гілка «врятувати прогін збуренням при T=1.0» ніколи не спрацьовує.
3. Гілка «спробувати м'якше збурення при T=0.6» ніколи не спрацьовує.
4. Керування завжди доходить до найгрубішого запасного варіанту: взяти рекорд,
   підняти **одну випадкову** трубу на два діаметри, полікувати. Тобто після
   тупика променевого пошуку пул наповнюється майже копією того самого рішення,
   з якого пошук щойно не зміг вийти.

Тобто аварійний вихід із тупика зараз робить протилежне тому, для чого його писали:
замість диверсифікації дає мінімальне збурення. Наскільки часто це спрацьовує — видно
в логах за рядком `[EMERGENCY] Beam search deadlocked`.

**Виправлення**: `forced_rescue = None if res1.failed else res1.solution` (і так само
для `res2`). Два рядки.

**Чому це не спіймали тести**: `_emergency_respawn` не покритий (рядки 1026–1059
у списку `Missing`). Разом із виправленням потрібен тест, який перевіряє, що рішення
кіка потрапляє в пул, — інакше наступний рефакторинг контракту зламає це знову.

**Чому це не спіймав `ruff`**: `isinstance(x, tuple)` — синтаксично бездоганний код.
Жоден лінтер не знає, що `smart_perturbation_kick` більше не повертає кортеж.
Від такого класу помилок рятує або анотація типу повернення (`-> KickResult`) і `mypy`,
або тест. Анотація дешевша: одна на десять методів `KickStrategies`.

### 2.2 SHOCK і BOTTLENECK повідомляють «успіх» там, де нічого не зробили

З 36 місць, де `kicks.py` повертає результат, **31 користується `KickResult.failure()`,
а 5 — ні**:

```python
# kicks.py:18, 21, 36 (forcing_hand_kick) і 46, 49, 85 (upstream_bottleneck_kick)
if not crit_node or crit_node == "ERR": return KickResult(indices, set())
if not path_pipes:                      return KickResult(indices, set())
if not locked:                          return KickResult(indices, set())
```

`KickResult(indices, set())` — це `failed == False` з рішенням, **рівним вхідному**.
Для `_apply_kick` це успішний кік. Далі за кодом:

* `self.selector.note_success(strategy)` — UCB1 отримує нагороду за нічого;
* `gradient_squeeze` запускається на рішенні, яке вже зійшлося, — чисті витрати симуляцій;
* `kick_memory.note_failure` не викликається, тобто пам'ять кіків не вчиться;
* у логах це виглядає як застосована стратегія, хоча вектор не змінився.

Для восьми інших стратегій та сама ситуація повертає `failure()` і обробляється правильно.
Тобто дві найчастіші стратегії (SHOCK — `FALLBACK_KICK`, BOTTLENECK — у всіх трьох пулах)
мають окрему, тихішу і дорожчу семантику невдачі.

**Виправлення**: замінити п'ять `return KickResult(indices, set())` на
`return KickResult.failure("No targets on critical path")`. Це **змінює поведінку**
(інша статистика UCB1, інша кількість симуляцій), тому потребує A/B на еталоні Hanoi —
але змінює її в бік, який замислювався.

### 2.3 Два пороги «велика мережа» пройшли повз `NetworkProfile`

Етап 8 (§25.1) звів вісім місць до одного `NetworkProfile.is_large`. Два не звів:

```python
# local_search.py:268
if self.ctx.num_pipes > 200:
    down_limit = min(down_limit, 40)

# local_search.py:283
if self.ctx.num_pipes <= 200:
    safe_up_limit = min(len(path_pipes), 15)
```

`200` — це межа MEDIUM/LARGE із `NETWORK_CLASS_BOUNDS`, тобто буквально те саме,
що `profile.is_large`. Зараз зміна межі в `context.py` тихо розійдеться з `swap_search`.

**Виправлення**: `if self.ctx.profile.is_large:` і `if not self.ctx.profile.is_large:`.
Поведінка не змінюється (межа та сама), тому еталон має збігтися побітово — це
безкоштовна перевірка правильності правки.

### 2.4 `is_late_game` рахується двома різними формулами

```python
# orchestrator.py:313 — у run()
self.is_late_game = self.progress_ratio > 0.5

# orchestrator.py:614 — у _apply_kick()
is_late_game = self.progress_ratio >= 0.5
```

Локальна змінна в `_apply_kick` затінює поле, і межа в них різна. Рівно на
`progress_ratio == 0.5` два методи бачать різні фази прогону. На практиці точна
рівність майже недосяжна, але це саме той клас розбіжності, який потім шукають годинами.

**Виправлення**: прибрати локальну змінну, читати `self.is_late_game`.

### 2.5 Блок перед циклом у `run()` не має жодного ефекту

```python
# orchestrator.py:266–273, одразу перед while True
if self.max_sims != float('inf'):
    if self.progress_ratio > 0.8:
        self._migration_interval_sims = max(1000, self.max_sims // 100)
    else:
        self._migration_interval_sims = max(1000, int((self.max_sims // 20) * (1.0 - 0.6 * self.progress_ratio)))
else:
    self._migration_interval_sims = 15000
```

`self.progress_ratio` ініціалізується нулем у `__init__` і до цього місця не змінюється,
отже гілка `> 0.8` **недосяжна**. Решта блоку теж нічого не дає: при скінченному
`max_sims` той самий розрахунок повторюється всередині циклу (рядки 317–322) до першої
перевірки інтервалу, а при `max_sims == inf` він присвоює 15000 — те саме значення, що
вже стоїть у `__init__`.

Тобто 8 рядків, які виглядають як налаштування, не впливають ні на що. Плюс той самий
розрахунок записаний двома різними виразами: `self.max_sims // 100` перед циклом і
`base_interval // 5` (де `base_interval = max_sims // 20`) усередині. Це те саме число.

**Виправлення**: видалити блок; винести розрахунок у метод `_migration_interval()`.

### 3.2 Три константи `Verdict`, які ніхто не створює і не читає

`acceptance.py:45–48`:

```python
HOPELESS_PRESSURE = "HOPELESS_PRESSURE"
EXPLOSION = "EXPLOSION"
UNUSABLE = "UNUSABLE"
```

Жодна з трьох не повертається з `classify()` і не порівнюється в `_apply_kick`.
Рішення «безнадійний тиск» і «вибух вартості» приймаються **до** `classify`, окремими
викликами (`is_hopeless_pressure`, `explosion_threshold`), із власними `return`.

При цьому docstring модуля обіцяє: «Плюс три розв'язки-відмови, які обриваються раніше:
`HOPELESS_PRESSURE`, `EXPLOSION` і `GHOST_VETO`». Тобто документація описує дизайн,
якого в коді немає — а це гірше за відсутність документації.

**Два чесні варіанти**, обирати треба свідомо:

* **прибрати** дві константи й виправити docstring — мінімальна правка, нуль ризику;
* **довести до кінця**: перенести обидві перевірки в `classify`, щоб усе рішення про
  прийняття було в одному місці. Це те, заради чого `AcceptancePolicy` створювався,
  але це змінює порядок обчислень (`is_hopeless_pressure` зараз рахується до heal,
  а `explosion_threshold` — після), тому потребує A/B.

## 5. Читабельність: що заважає зараз

### 5.1 `orchestrator.py` тримає чотири різні відповідальності

| Клас | Рядків | Про що |
|---|---|---|
| `SeedFactory` | 118 | побудова початкових рішень |
| `IslandWorker` | 925 | цикл пошуку одного острова |
| `AnalyticalSolver` | 310 | оркестрація островів, живий моніторинг, звіт |

Три класи без спільного стану, зчеплені лише тим, що лежать в одному файлі. Розділення
на `seeds.py` / `island.py` / `orchestrator.py` — механічна операція, яка знімає MI 0.00
у двох із трьох частин одразу, без жодної зміни логіки.

### 5.2 `solve_standalone`: 221 рядок, сім справ

За порядком у тілі: розподіл бюджету → створення `Manager` → побудова задач →
**цикл живого моніторингу на 100 рядків** (друк статусу + збір архіву + `ui_callback` +
`history`) → збір результатів із трьох джерел → фінальний поліш → друк підсумку.

Цикл моніторингу — найбільший і найменш пов'язаний із рештою шматок. Він не приймає
жодного рішення про пошук: він читає `shared_progress` і показує. Виносити його
безпечно, бо він нічого не мутує, крім `self.history` і локальних `global_best_*`.

### 5.3 `kicks.py`: десять стратегій без контракту аргументів

`_apply_kick` збирає один словник на дев'ять ключів і передає його всім кікам однаково.
Кожна стратегія розбирає його вручну:

```python
failed_pipes = kwargs.get('failed_pipes', {})
boosted_pipes = kwargs.get('boosted_pipes', {})
current_round = kwargs.get('current_round', 0)
```

Наслідки: опечатка в ключі мовчки дає дефолт; неможливо побачити, які аргументи
стратегія справді читає, не прочитавши її тіло; `forcing_hand_kick` оголошує `**_kwargs`,
решта — `**kwargs`, і ця різниця нічого не означає.

Це саме та ціна за єдиний диспетчер, про яку чесно написано в коментарі §13. Вона
знімається одним `@dataclass KickArgs` із дев'ятьма полями: сигнатура стає
`def upstream_bottleneck_kick(self, indices, args: KickArgs) -> KickResult`, і кожна
стратегія читає `args.failed_pipes` — з перевіркою імені на етапі імпорту, а не мовчки.

Побічно це закриває §2.1: анотація `-> KickResult` зробила б помилку `isinstance(res, tuple)`
видимою для будь-якого редактора.

### 5.4 Два способи щось вивести

`orchestrator.py` містить **24 виклики `print()`** поряд із `self.ctx.log()`. Правило
зараз неписане: `IslandWorker` логує через `ctx.log`, `AnalyticalSolver` друкує через
`print`. Працює це тому, що `main.py` і `gui.py` підміняють `sys.stdout` на `DualLogger`
і `GUIStream` відповідно. Наслідок: солвер неможливо використати як бібліотеку без
захоплення глобального `sys.stdout`, і в тестах `AnalyticalSolver` доводиться ловити
`capsys` замість того, щоб передати заглушку.

### 5.5 `readme.md` розійшовся з кодом на п'ять місяців

Файл датований 16.04.2026, 1 287 рядків. Він описує:

* `ga_config.py`, `ga_data.py`, `ga_utils.py`, `GAConfig`, `load_config` — усе перейменовано на етапі 11;
* `is_ghost_solution(x, cost)` — параметр `cost` прибрано на етапі 1;
* `baseline_bonus` — прибрано на етапі 1;
* епохи — прибрані на етапі 9;
* `evaluate()` зі штрафом — прибрано на етапі 12.

Для роботи над дисертацією це найдорожчий пункт усього списку: документ, який виглядає
докладним і при цьому описує неіснуючу систему, гірший за його відсутність — на нього
спираються, і він підводить у найневдаліший момент.
